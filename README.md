# MaterialRAG

面向材料文献的**检索增强问答 + 结构化数据抽取**框架。内置字段词典覆盖铝合金等常见体系
（成分 / 工艺 / 组织 / 性能），但**不绑定任何一套具体字段**：换体系、换表格都是改模板，不改代码。

两条主线：

| 能力 | 说明 |
| --- | --- |
| 文献问答 | 把 PDF 解析、切块、向量化，支持混合检索（向量 + BM25）与带引用的问答 |
| 数据抽取 | 从文献中抽取「成分 — 工艺 — 组织 — 性能」数据，**逐字段附原文引文**，按目标 Excel 的表头写入，写入前出 diff |

设计上有一条硬约束：**文献与推理默认全部在本机完成**。大模型走本机 LM Studio，向量化走本机 CPU 模型，不依赖任何云端服务。

## 二、快速开始

> **首次运行：`config.yaml` 不在仓库里**（它含密钥，已列入 `.gitignore`）。
> 先复制模板再改：
>
> ```bat
> copy config.example.yaml config.yaml
> ```
>
> **密钥请用环境变量 `RAG_API_KEY`**，不要写进 `config.yaml`——这个仓库是公开的：
>
> ```bat
> setx RAG_API_KEY "你的密钥"        :: 设一次，之后新开的窗口都生效
> ```
>
> 其余按需改 `llm` 段：本地 LM Studio 填 `http://127.0.0.1:1234/v1`（`api_key` 留空即可，它不校验），
> 并在 LM Studio 里加载对话模型、把 `llm.model` 填成该模型名；`embedding` 默认也走 LM Studio，
> 需要再加载一个 embedding 模型。
>
> 用云端 API 时：`base_url` **必须带 `/v1`**，并**清空 `gen.reasoning_effort`**（LM Studio 专用，
> 云端收到会 400）。**推理型模型（qwen3 等）依赖 `gen.disable_thinking` 关思考**——不关会长时间
> 无响应（实测 qwen3.8-max 面对 101 字段抽取任务思考超过 200 秒仍无输出，关掉后 58 秒完成）。
> 换 embedding 模型后必须重建索引（维度会变）。

### 0. 准备（只需一次）

需要 **Python 3.12**。在项目目录里建一个独立虚拟环境 `my_venv`：

```bash
cd <你的项目目录>

# 建虚拟环境（Windows 上若 python 不是 3.12，可用 py -3.12 -m venv my_venv）
python -m venv my_venv
my_venv\Scripts\activate                      # Linux/macOS：source my_venv/bin/activate

# 依赖：torch 必须单独装 CPU 版（PyPI 上的同名包是约 2GB 的 CUDA 版）
python -m pip install torch==2.14.1 --index-url https://download.pytorch.org/whl/cpu
python -m pip install -r requirements.txt

# embedding 模型（约 91 MB，走 hf-mirror 直链；已下载则跳过）
python scripts/fetch_embedding_model.py
```

> 不激活也可以直接使用 `my_venv\Scripts\python.exe`（下文命令都写成这种形式），
> 效果与先 `activate` 再敲 `python` 完全相同。

### 1. 让 LM Studio 提供接口

在 LM Studio 中加载一个对话模型，打开 **Developer → Start Server**（默认端口 1234）。
然后在 `config.yaml` 里确认：

```yaml
llm:
  base_url: "http://127.0.0.1:1234/v1"
  model: ""        # 留空 = 自动取 /v1/models 的第一个模型
```

自检连接：

```bash
python run.py status
```

### 2. 建索引

把 PDF 放进 `data/raw_pdfs/`，然后：

```bash
python run.py ingest
```

### 3. 问答

```bash
python run.py ask "6061 铝合金的固溶与时效工艺参数分别是多少？"
```

### 4. 抽取数据（Excel 按需）

默认**不碰任何文件**，结果直接显示在终端：

```bash
python run.py fill                      # 结果直接显示（默认范围 = 表格 + 含数据段落）
python run.py fill --json               # 同时输出完整 JSON
python run.py fill --mode table --max-chunks 3   # 想快：只抽表格，且只抽 3 块先看质量
```

抽取是全流程唯一耗时的环节，规模（范围 / 块数 / 并发）怎么控见「十一、控制抽取规模」。

只有当你决定写入表格时，才需要目标 Excel 的路径：

```bash
python run.py fill --excel "C:/path/铝合金数据库.xlsx"          # 只出预览与 diff，不落盘
python run.py fill --excel "C:/path/铝合金数据库.xlsx" --yes    # 确认后落盘（自动备份）
```

### 5. 图形界面

在项目根目录**双击 `start_web.vbs`**（推荐）：不开任何命令行窗口，后台用 `pythonw`
启动服务；**服务就绪后写 `data/output/web.ready` 标记**，脚本检测到标记才打开浏览器
（实测约 1.7 秒）。

启动检测迭代过几轮，每轮都是被真实故障逼出来的：
1. 固定等 2.5 秒 —— 索引变大后变慢，浏览器先到 → "拒绝连接"；
2. 轮询 `/api/status` —— VBS 里 WinHttp 的代理/超时不可控，一次探测失败就耗到上限，
   用户侧表现为"双击后很久没反应"；
3. **检测就绪标记文件** —— 纯本地文件操作，毫秒级，没有网络语义可出错；
4. **标记里带服务进程 pid**（当前）—— 进程被任务管理器强杀 / 崩溃时标记会残留，
   脚本用 WMI 核对 pid 是否还活着，死了就删掉标记重新拉起服务，而不是把浏览器
   指到一个已经没人监听的端口。

> ⚠️ **`start_web.vbs` 必须保持纯 ASCII**：不能出现中文、不能有全角标点。
> Windows Script Host 按系统 ANSI 代码页（cp936/GBK）解析 `.vbs`，不认 UTF-8。
> UTF-8 中文被当成 GBK 双字节，**奇数个汉字**会留下一个悬空的前导字节，把字符串的
> 收尾引号吞掉，脚本在执行任何一行之前就报 `800A0409 未结束的字符串常量`。
> 中文说明放 README / 网页界面，日志文案由 Python 端以 utf-8 写。
> `scripts/selftest.py` 第 15 组断言（纯 ASCII + 每行引号成对）专防这个回归。

`data/output/launch.log` 记录每次启动的分阶段耗时（启动、就绪、开浏览器），
排查"启动慢"直接看这个文件。

启动耗时做过一轮优化（2026-10-27）：把 `pandas`(304 ms) / `openpyxl`(181 ms) / `pymupdf`(63 ms)
从启动路径挪到首次使用时加载，`import rag.web.app` 从 685 ms 降到 351 ms；
`_probe_port` 对本地回环改用 0.1 s 超时（原本 0.35 s 让每次状态查询都白等），
健康检查加 3 s 缓存。整体从 2.56 s 降到 **2.00 s**。

**服务生命周期**（三种情形，行为不同）：

| 情形 | 服务 | 抽取任务 |
|---|---|---|
| 空闲时关页面 | 15 秒后自停（宽限见 `web.shutdown_grace_s`） | — |
| **抽取中关页面**（含被别的窗口冲掉） | **不停**，任务跑完为止 | 继续跑 |
| 浏览器崩溃/断电（没发关闭信号） | 心跳兜底：无心跳 3 分钟自停，但**有任务在跑时不停** | 继续跑 |

刷新页面不会误停（新页面连上即取消关闭倒计时）。**重新打开页面会自动接管正在跑的任务**：
进度、已用时间、最终结果都不丢，「已用」接的是任务真实起点，不会从 0 重数。

关掉页面后服务会自停（约 15 秒），**1 分钟后再打开，上一次抽出来的数据仍然在结果面板里**：
每批结果都会写到 `data/output/last_extract.json`（本地文件，不上传），下次启动原样读回；续抽时按表头对齐后接在上一批后面。落盘失败会写进 `web.log`（以前静默吞异常、日志还写「已落盘」，刷新后看到的其实是上一批）。
续抽的批次会接在上一批后面累加，不会只剩最后一批。点「开始抽取」才算全新开始，
会同时清空这一份和浏览器的进度记录。还原时限 `web.restore_ttl_s`（默认 24 小时）——
隔太久就当作换了一批文献，不再把旧结果摆出来。

- 也可在界面「索引 → 服务生命周期」点「立即停止服务」。
- 日志：`data/output/web.log`（静默启动没有控制台，出问题看这里）
- 启动入口只有 `start_web.vbs`；不需要任何 .bat 停止脚本。

### 顶部「模型连接」芯片

绿点 + 模型名 = 已连接；红点 + **未连接** = 连不上。**把鼠标停在芯片上会显示具体原因**
（`未连接：<错误信息>`），服务端同时会往 `web.log` 写一行 `[llm] 健康检查失败：…`，
静默启动没有控制台，靠这两处查。

一次网络抖动导致的"未连接"**不用刷新页面**：心跳每 15 秒带回一次模型状态，
恢复后芯片会自动变绿（`health` 有 60 秒缓存，几乎不产生额外请求）。

### 刷新页面为什么有时变慢

页面加载时会接管上一个任务，**把已跑完的结果原样还回来**，避免手滑刷新丢掉几十分钟的成果。
结果里带逐字段的原文证据，几十块就有 100 KB ~ MB 量级，每次刷新都传一遍、解析一遍、
再重绘整张表，页面就会明显变慢。

所以接管有**时效**：`web.adopt_ttl_s`（默认 600 秒）。10 分钟内刷新 → 结果照常还回来；
超过 10 分钟 → 只还原"已抽到哪"（`done_ids`，用于「继续抽取」），不再搬运结果，
刷新因此保持轻快。跑完立刻刷新属于前者，这是设计上要保的场景。

想在终端里看实时日志时用前者之外的方式：

```bat
my_venv\Scripts\python.exe -m rag.cli serve
```

界面地址：<http://127.0.0.1:8848>；这种方式停止按 `Ctrl+C`。

界面有三个视图：**抽取**（模板 + 文献 + 结果）、**问答**（纯 RAG，不抽取不写表）、
**索引**（状态与重建索引）。支持 `?view=ask` / `?view=index` 直达、`?theme=dark` 固定深色。

关于端口的两点说明：

- **重复双击不会报错**。若 8848 上已有本项目的服务在跑，脚本会识别出来、直接帮你打开浏览器，
  不会抛 `WinError 10048`。要重启的话，先在原窗口按 `Ctrl+C`。
- 若 8848 被**别的程序**占用，脚本会明确提示并建议换端口：
  `my_venv\Scripts\python.exe -m rag.cli serve --port 8849`

## 三、核心设计决策（为什么这样做）

### 1. 目标表的表头就是抽取契约（不写表也能用）

程序不硬编码字段清单：**给了 Excel**，就读表头，把每一列匹配到内置字段词典，
匹配不上的列按「自定义列」原样送模型——你随时可以在表里加一列，不需要改代码。

```
Excel 表头:  合金牌号 | Si(wt.%) | 时效温度 | 抗拉强度Rm(MPa) | 我的新列
                  ↓          ↓          ↓              ↓            ↓
抽取 key:    alloy   composition.Si  process.aging_temp  properties.UTS  custom.我的新列
```

**没给 Excel** 时（默认情况），程序直接使用内置字段词典的全字段
（成分 / 工艺 / 组织 / 性能约 70 项）抽取，结果只显示在终端或界面上，不产生任何文件。
需要入库时再补 `--excel`，字段按 key 自动对齐到你的表头。

### 2. 模型只做「转录」，不做「计算」

提示词要求模型把原文的数值表示**原样抄写**并给出证据片段：

```json
{"properties.YS": {"raw": "276", "quote": "the yield strength reached 276 MPa"}}
```

数值解析、区间识别（`0.5~0.6` → low/high，**不取中值**）、上界下界（`≤0.05`）、
单位归一（`wt%` → `wt.%`）全部由 `normalize.py` 的确定性代码完成。
把算术从模型手里拿走，就消灭了一整类错误来源。

**特殊值在结果表格里怎么填**（写进 Excel 的 `value` 列，全部保留原文写法）：

| 原文写法 | 解析类型 | 表格里的值 | 内部结构 |
|---|---|---|---|
| `380` | single | `380`（数值） | value=380 |
| `0.5~0.6`、`0.5-0.6`、`0.5–0.6`、`10 至 20` | range | `0.5~0.6`（文本，原文照抄） | low=0.5, high=0.6 |
| `≤0.05`、`<0.05`、`<=0.05`、`不超过 0.2` | upper_bound | `≤0.05`（文本） | high=0.05 |
| `≥300`、`>300`、`>=300`、`at least 250` | lower_bound | `≥300`（文本） | low=300 |
| `380 ± 2` | mean_pm | `380 ± 2`（文本） | mean=380, pm=2 |
| `Bal.`、`余量` | text | `Bal.`（文本） | value=原文 |

要点：**区间和界限值不会被折算成单个数**（不取中值、不丢弃比较符），表格里看到的就是
原文写法，`parsed` 里另存 low/high 供程序使用。这些单元格在 Excel 里是**文本**，
做数值统计需先拆分——刻意的取舍：宁可让你多一步，也不让程序替你猜一个不存在的数。

同一条原则的另一个表现：**原文未提及的字段直接省略该键**，绝不用推测值填补。

### 3. 每条数据必须能在原文中逐字找到

`verify_quote()` 会在送入的文献片段里做全半角/空白归一化后的子串查找。
找不到的字段被标记 `unverified`，**默认不写入数据表**，但会出现在证据明细里供你复核。

### 4. 证据校验之外，还有一层物理合理性校验

`verify_quote` 只能证明"这段引文来自原文"，证明不了"它说的就是这个字段"。
实测踩到的坑：**铝合金文献的成分表普遍不列 Al**（Al 是余量，按领域惯例写 Bal. 或不写），
但模板里有 Al 字段，模型就从正文或表格别处抓一个数字填上（出现过 Al=20 wt.%、40 wt.%），
而它的引文在原文里逐字存在——**证据校验照样通过**。

因此新增一层物理合理性校验（`rag/extract/normalize.py` 的 `sanity_issue` / `composition_sum`）：

| 规则 | 触发 |
|---|---|
| 成分 wt.% 超出 0~100 | 报「超出 0~100」 |
| 基体元素（Al）低于 50 wt.% | 报「偏低……原文可能未列 Al（余量）或抽取错位」 |
| 各成分 wt.% 合计 > 110 | 报「成分合计超过 100」 |

**处理方式分三档**（数值一律不改，但"明显不可能"的值不进入记录）：

| 情况 | 处理 | 原因 |
|---|---|---|
| 成分 wt.% **为负或超过 100** | **整字段跳过** + 警告「已跳过该字段」 | 质量分数不可能如此，属错误映射而非可疑值 |
| Al 只有 20~40 wt.% | 仅警告（值保留、仍可信） | 截断版表格里 Al 可能真是这个数 |
| 引文在原文中找不到 | 值保留但标不可信 | 可能抄错，也可能片段被截断，留人工判断 |

跳过一个字段不会影响同一行里的其他字段；若一行所有数值字段都被跳过，该行不会产出记录。

实测踩到的第二类坑：文献里有一张 `Table 2 The ΔGseg`（晶界偏聚自由能，kJ/mol，含 −9.127 这类负值），
模型把它塞进了 `Mg`/`Si`/`Cu` 成分字段，引文逐字命中、证据校验通过。现在这类值会被判不可信。

**更彻底的做法：抽铝合金时别让模板要 Al。** 新增了 `al_no_balance.yaml`
（界面显示名「铝合金无余量模板」，92 字段）——基于内置模板删掉了 `Al` / `Al_pred`，
模型不再被逼着填一个原文没有的字段，从源头杜绝这类假数据。
（`material_default` 内置模板保持 94 字段不动，它是自测回归基线。）

Al 数据的后续处理建议：在 Excel 里统一补一列填 **`Bal.`**（原文语义就是余量）。
**不建议用 `100 − 其他成分之和` 反算**——那是"计算"，违反本项目铁律，
且微量元素常漏抽，反算出来的值看着精确其实是错的。

### 5. 表格参考上下文与跨块合并（只作用于抽取链路）

**表格参考上下文**：表格常把工艺条件、单位、样品说明写在正文里，表格单独成块后
模型看不到，于是让工艺字段空着、或把预测值当实测值。现在抽表格块时会附上**同页正文**
作为参考上下文，并在提示词里明确标注「仅供理解、不得从中抽取」（铁律第 11 条）。

实现要点：只读 `store.chunks` 建「(文献,页) → 正文」索引，**不改 chunk、不重建索引**，
所以检索与召回完全不受影响。配置：

```yaml
extract:
  table_context:
    enabled: true
    max_chars: 400      # 每张表附带的同页正文上限
```

**跨块合并**：同一样品的成分常在一张表、性能在另一张表。旧实现按「全部字段值」做指纹，
两条记录字段集合不同 → 永远合不上，结果是一条只有成分、一条只有性能。
现在改为按 **（文献, 合金牌号）** 合并，并做冲突检测：

| 情况 | 行为 |
|---|---|
| 同文献同牌号、字段不重叠 | 合并成一条（成分 + 性能拼齐） |
| 同文献同牌号、同名字段值不同 | **不合并**（不同工艺条件的数据，各自保留） |
| 完全重复（同一块被重复抽） | 去重成一条 |
| 无牌号 | 不合并（身份不明，宁可保留也不误拼） |

**结构化输出**：抽取调用可带 `response_format={"type":"json_object"}`（配置
`extract.json_object_mode`，默认开），减少"输出带解释文字"导致的解析失败；
本地服务不支持时自动去掉该参数重试一次。问答链路不传该参数，行为不变。

### 6. 写回 Excel 遵循「先填后验 diff」

```
读取表头 → 生成 schema → 抽取 → 预览行 + 证据明细
   → 你确认 → shutil.copy2 备份 → 追加写入 → 重新快照 → 逐 cell diff
   → 报告「非预期变更数」，正常必须为 0
```

写入按牌号**回填已有行的空格**，回填不了才追加到末尾，不覆盖任何已有值；`diff` 会明确指出哪些单元格被改动。

## 六、性能实测（参考机：16 核 CPU / 32 GB 内存 / 无独显）

以下为真实测量值，不是估算：

| 环节 | 实测 | 结论 |
| --- | --- | --- |
| embedding（nomic-embed-text，经 LM Studio） | **52 条/秒**（实测）；重建 10916 块用 161 秒 | 编码不再是瓶颈；`local` 后端（bge-small-zh）约 45~49 块/秒 |
| 向量内存 | 每块约 2 KB | 10 万块约 200 MB，32 GB 内存不是瓶颈 |
| 混合检索 | 毫秒级（numpy 矩阵乘 + BM25） | 几千篇无压力 |
| 数据抽取 | **单块 9~211 秒**（5 篇文献 / 30 个表格块实测） | **真正耗时的环节，且长尾极重** |

抽取耗时的实测分解（同一张多列大表，5 条记录）：

| 变量 | 实测 | 说明 |
|---|---|---|
| 94 字段模板 | 210.8 秒 | 输出长，解码时间主导 |
| 精简到 7 字段 | 102.6 秒 | 输出砍半 → 耗时砍半，但仍有约 100 秒固定开销 |
| 短表格块（414 字符） | 9.1 秒 | 小表很快，慢的是少数大表 |

结论：**耗时 ≈ 块数 × 每块时间，且被少数大表支配**。所以先控块数（见第十一节），再精简字段。

文献容量上限主要由**磁盘**而非性能决定：几千篇完全没问题；上万篇（千万级块）
才需要考虑换 FAISS 分片/量化等更省的向量库。

## 七、已知限制（如实说明）

1. **抽取质量取决于所用模型**。框架保证的是「有证据才写、没证据不写」，
   但不能保证模型把原文所有的数据都找齐。漏抽比错抽更容易发生。
2. **表格抽取依赖 PDF 是否带线框**。扫描版/无边框表格识别率会下降；
   这类文献建议先做 OCR 或改用别的解析器。
3. **中文按字分词**。BM25 通道对 2~4 字材料术语够用，但不如专业分词器细腻；
   语义部分由向量通道兜底。
4. **重排模型默认关闭**，开启需额外下载约 1.1 GB 的 `bge-reranker-base`。
5. **`local` 后端的向量化只取每块前 512 token**（`max_length=512`），超长块后半段不进向量。
   `lmstudio` 后端不受此限（nomic 支持 8192 token，整块都进向量）——这也是默认改用它的原因之一。
6. **跨语言检索不可靠**：实测 nomic 与 bge-m3(GGUF) 的「中文查询→英文文档」区分度都接近 0，
   中文提问依赖 `ask()` 里的自动翻译（`_translate_query`）先把问题转成英文再检索。
7. **更换 embedding 模型必须重建索引**（维度或语义空间变了，旧向量作废）。
   只重算向量不必重新解析 PDF：读出 `chunks.jsonl` → 重新编码 → 覆盖 `vectors.npy`。
8. **写 Excel 不是原子操作**：`openpyxl` 直接保存到目标文件，保存中途崩溃可能损坏原表。
   默认会先备份到 `data/output/backups/`，可用备份恢复。
9. **CPU 环境**。向量化用 LM Studio 跑 nomic（768 维，52 条/秒），瓶颈在 LLM 生成本身，
   取决于 LM Studio 里加载的模型大小；换云端 API 后瓶颈转为网络与 token 计费。

## 九、动态抽取模板

抽取字段不再写死。模板可以放 `data/schemas/*.yaml`，也可以在界面里粘贴 YAML/JSON 后直接抽（不落盘也行）。

最小示例（存成 `data/schemas/my.yaml` 就能在界面和命令行里选中）：

```yaml
name: 我的合金模板
key_field: alloy
groups:
  - key: chemical
    label: 化学成分
    bucket: composition        # composition|process|microstructure|properties|meta
    fields:
      - { key: Si, label: Si, type: number, unit: wt.%, aliases: [硅, Silicon] }
  - key: props
    label: 力学性能
    fields:
      - { key: UTS, label: 抗拉强度, type: number, unit: MPa }
```

### 界面里手动加字段（不限于模板预设）

抽取页左侧「字段」区支持直接手输字段名，回车即加：

| 输入 | 结果 |
|---|---|
| `Si` | 自动匹配内置词典 → `Si`，number，wt.% |
| `抗拉强度` | 中文名映射到内置字段 → `UTS`，number，MPa |
| `自定义指标:number:%` | 自定义字段：名称 + 类型 + 单位 |
| `Ni, Cu, 硬度HB` | 逗号分隔，一次加多个 |
| 已有字段重复输入 | 跳过并在下方提示「已存在」 |
| 类型写错（`X:乱写`） | 明确报错，不落盘 |

每个字段显示为带 `×` 的标签，点 `×` 即删除；删除后若分组空了，该分组自动移除（模板不允许空组）。
所有增删都走 `POST /api/schema/edit`：后端解析 YAML → 改结构 → 重新校验 → 回传新 YAML，
前端用它刷新编辑框与标签，**唯一事实源始终是那段 YAML**，所以手输和直接编辑 YAML 不会打架。

**字段分类与排序（2026-10-17 新增）**：

- 字段区上方有 **全部 / 成分 / 组织 / 工艺 / 性能** 五个筛选按钮，单选，只看该类字段
  （「合金牌号」这类标识字段只在「全部」里出现，它不属于四个数据桶）；
- **字段标签可直接拖拽排序**：拖 A 放到 B 上 = A 移到 B 前面，支持跨分类拖
  （切回「全部」才能拖到别的分类）。顺序改动走后端 `move` 操作写回 YAML；
- **添加字段的目标分类跟随筛选按钮**：选了「性能」再输入，字段就进性能组；
  停在「全部」时无法添加（不知道该进哪个桶），会提示先选分类；
- 字段顺序 = 送进提示词的顺序，把最关心的字段排前面即可。

要点：**筛选按钮管「看」，也管「加」**——两者是同一个选择，不再单独选目标组。

**另存为模板的同名覆盖**：点「另存为模板」且名字与现有用户模板相同时，**覆盖原文件**
而不是新建——改字段后另存同名就是更新，不会出现两个同名模板。

**RE 字段 = 其他元素**（自定义模板里的常见写法）：字段清单之外的成分列（Be、Ca、Sr、Ce 等）
由模型按「元素=数值」合并写进 RE（text 类型，分号分隔，如 `Be=0.05; Sr=0.01`），
不会丢数据。规则写在抽取提示词第 10 条；模板里 RE 带 hint 说明。

模板下拉里显示的字段数对**当前选中模板**是实时的：增删字段后立刻跟着变（取校验结果而非模板文件快照），
其它未选中的模板仍显示文件里的原始数量。

要点：
- **分组只是展示层**，数据落到 4 个固定桶里（成分/工艺/组织/性能），所以写回、缓存、前端都不需要改结构；
- 字段类型：`number | text | range | enum | bool | list`；`enum` 必须给取值；
- 内部字段名 = `桶.字段`（`meta` 组除外，用裸名如 `alloy`），同名冲突会在校验时报错；
- Schema 优先级：**指定目标 Excel → 表头覆盖模板** > 指定模板 > 内置 94 字段模板。

命令行同样支持：

```bat
my_venv\Scripts\python.exe -m rag.cli fill --schema 我的合金模板 --mode table
my_venv\Scripts\python.exe -m rag.cli fill --schema al_no_balance --mode table
my_venv\Scripts\python.exe -m rag.cli fill --schema data\schemas\my.yaml --excel target.xlsx --yes
```

## 十、导出与基础清洗

结果面板右上角「导出」，支持 **CSV 直接下载** 与 **Excel 写入**（路径不存在则新建；已存在则追加，写入前自动备份、写后逐格 diff，报告非预期变更数）。

清洗是**可选、可审计**的字符层修正，不动数值语义：

| 开关 | 做什么 | 例子 |
|---|---|---|
| 去重 | 删掉完全重复的行（同批重复抽取的主要来源） | 重复行只留一条 |
| 剔除未核验 | 未通过原文逐字核验的字段不进表 | 证据不通过 → 空 |
| 去多余空格 | 首尾空白清除、内部连续空白压成一个 | `  0.62  ` → `0.62` |
| 全半角归一 | NFKC + 统一减号/波浪号 | `８０．５` → `80.5` |
| 修数字内空格 | 修被空格劈开的数字 | `1. 59` / `0 . 62` → `1.59` / `0.62` |

**不做**：单位换算、取中值、改写数值。`0–2.40`、`380 ± 2`、`Fig. 5`、`Al₁₅(FeMnCr)₃Si₂` 这类都会被原样保留（有断言守着）。

导出后界面会显示「扫描 N 格 / 修正 M 格 / 各项规则命中数」，可以据此复核改了什么。

### 行级常识校验：物理不可能才删，可疑只标注

写入前每一行都过一遍常识检查（`rag/extract/quality.py`），分两档：

| 档 | 触发条件 | 处理 |
|---|---|---|
| 硬（剔除整行） | 抗拉强度 < 屈服强度；强度 ≤ 0；延伸率超出 0~60%；硬度与强度差一个数量级（UTS/HV 不在 1.5~7.5）；温度/时间越界；成分合计 >105 | 整行不写入，原因进 `dropped` |
| 软（保留 + 提示） | T6 状态却只有 150 MPa 以下、屈服/抗拉 <0.35、UTS/HV 偏离 2.4~4.6、延伸率 <3 却抗拉 >450 | 写进 `warnings`，交人复核 |

**为什么不是"屈服强度 <200 MPa 就删"**：本库实测 293 条有屈服强度的记录里，58 条低于 200 MPa，
逐条看是自然时效（AA6016 四周 → 57/110）、欠时效（6082 → 64/178）、预时效（6013 → 185）——
全是热处理数据集最需要的低强度状态。一刀切会把"时效不足"的样本全删掉，只剩 T6。
所以低强度只在**状态明确且明显不符**时提示，不删数据。各状态的下限写在
`quality.py` 的 `YS_FLOOR_BY_STATE`，可用 `extract.row_checks.state_ys_floor` 覆盖。

### 表头识别：拆成「名称 + 单位」再判定

表头写法千奇百怪（`Elongation (%)`、`Elong. %`、`塑性指标`、`Si(wt.%)`），
现在不是拿整串去比，而是三步：

| 步骤 | 做什么 | 例子 |
|---|---|---|
| 拆 | 把名称与单位分开，单位只认**括号里**或**结尾空格后**，绝不从结尾字母猜 | `抗拉强度 Rm` 的 m 不当成"米" |
| 名 | 精确别名 → 元素式 → 去残留单位 → 词干（elongation/elongated 同根）→ 子串（中文≥3 字、英文≥4 字母，最长优先） | `Elong. (%)` → 延伸率 |
| 门 | 表头单位与字段单位必须**同量纲**（%、MPa、℃、h 不能混） | `Elongation (MPa)` 直接拒 |

表头实在认不出时，还有一层兜底：**按这一列的数值形状反推**。规则是三条全过才接受——
至少 3 个数值、80% 落在某字段的典型区间、且**只有唯一一个字段满足**。
例如 `塑性指标 (%)` 的 12.5/14/9.2 → 延伸率；而 `力学指标 (MPa)` 的 280/310/295
在抗拉与屈服之间分不开，就**放弃**、留作自定义列。反推出来的列会在 schema 里标
`inferred`，能查得到是猜的还是认出来的。

### 写入 Excel 时，表里的列名说了算

写表不是把模板的列原样照搬，而是**按目标表的表头定位单元格**。所以两边写法不同
（模板写 `Si`、你的表写 `Si (wt.%)` / `硅` / `Mg 含量`）时会自动对齐，
并在结果面板列出「列名对齐：Si -> Si (wt.%)」供你核对。

匹配只认两种确定性写法：**词典里的同义名**（硅 / 牌号 / 抗拉强度 MPa）和
**元素符号带单位尾巴**（Si(wt.%) / w(Si) / Mg 含量）。含糊的表头不会被猜成某一列——
宁可跳过并在结果里列出「跳过（表里没有对应列）：…」，也不擅自把值填进看起来像的那一列。

三种结果：

| 情况 | 行为 |
|---|---|
| 至少有一部分列对上了 | 按目标表表头写入，报告**实际写入的单元格数** |
| 一列都对不上 | **直接报错 400**，一行都不写，你的表保持不变 |
| 目标文件不存在 / 是空表 | 先按模板列名建表头，再写数据 |

> 曾经有个 bug 就出在这里：列名对不上时一个格子都没写，后端却返回成功、
> 界面显示「已写入 N 行」。现在任何"写入 0 个单元格"的情况都会按失败处理。

### 写入位置：先回填已有行，回填不了才追加

写入默认是 **upsert**，不是无脑追加：

| 情况 | 行为 |
|---|---|
| 表里已有同牌号的行，且本次要写的列在那一行是空的 | **填进那一行**（不新增行） |
| 那一行在同样的列上已有**不同的值** | 认为不是同一批数据 → 另起一行，绝不覆盖 |
| 表里有多个同牌号行，且没有能区分的列（如「文献」） | **不猜**，另起一行，并在结果里报「N 条无法判定归属」 |
| 牌号为空 / 表里没有这个牌号 | 另起一行 |

想精确回填就给表加一列「文献」（或「来源」），键会自动变成「牌号 + 文献」，
同牌号不同文献互不干扰；也可以在 `writeback.key_columns` 里显式指定主键列。
`writeback.upsert: false` 可退回旧的"一律追加"行为。

表末尾若有只是加了边框/底色、但没有值的空行，会保留原样、数据写在它们后面。

同一批结果**点两次「存入数据」就会真的写两遍**——程序不会替你删行，只会在结果里提示
「其中 N 行与表里已有行完全相同（仍然写入了，可能点过两次）」。要不要删由你决定，
因为判断"这是重复写入还是本来就该有两行"只能靠人。

导出在写入前会算一次**填充率**并显示（整体 + 低于一半的列）。`writeback.min_fill_rate`
设为大于 0 时，低于该比例直接拒绝写入——避免"写进去了"被当成"抽到了"。

### 工艺列为什么几乎是空的（以及怎么补）

工艺参数（固溶温度/时间、淬火、时效温度/时间）在论文里通常**只说一次**：写在 Experimental
段落里，而成分数据在另一张表。块级抽取一个块一次调用，看不到跨块信息，于是成分表那个块
只能抽出成分、实验段落那个块抽出的工艺又没有牌号 —— 结果工艺列几乎全空，同一批样品还被
拆成好几行。

现在多了一道**文档级工艺配方卡**（`rag/extract/process_card.py`）：

1. 每篇文献额外跑一次调用，把该文献报告的**全部工艺路线**抄成结构化卡片（带 quote）；
2. 补进缺工艺的记录，三级规则：牌号精确匹配 → 牌号包含 → 全篇只有一条路线时整篇共用；
3. 匹配不到、或文献有多条路线而牌号对不上时，**一律留空**；
4. 每条补进去的值都带出处标记（`per-alloy` / `paper-level`）并写进记录的 warnings。

同时，工艺/性能字段有了物理范围校验（`extract.quantity_ranges`）：时效温度=1、固溶温度=6
这类"把小时数写成温度"的值会被删掉并说明原因，不再原样落进表里。

**关于"填充率 95%"要说清楚**：分母里包含"文献根本没报告"的字段。以 14 列的表为例，
成分列在文献给了成分表时可以达到 95% 以上；工艺列在该文献确实报告了工艺时可以做到很高，
但如果文章只写"T6 处理"而没给参数，任何方法都填不出来（除非允许编造）；
像"晶间腐蚀"这种只有部分文献才测的列，全局 95% 在物理上不可能。

诚实的验收口径是两个数：`命中率 = 正确写入 / 文献报告了的值`，
`编造率 = 原文没有却写入 / 全部写入`（必须为 0）。只报一个"95%"而把编造混进去，这个数没有意义。

### 表格与上下文连接：一行一个样品

块级抽取会把同一批样品拆成好几条记录：成分表那个块出一条、性能表那个块出一条、实验段落那个
块出一条。实测 979 条记录里，342 条只有性能、441 条只有成分，三项齐全的只有 42 行 —— 数据都在，
只是没挂到一起。所以抽取之后多了这一步（`rag/extract/join.py`）：

| 步骤 | 做什么 | 是否用模型 |
|---|---|---|
| 样品级继承 | 同（文献, 标签）内，把成分/牌号补到缺的记录上（成分是样品属性，不是条件属性） | 不用 |
| 标签对齐 | `AA6082` 与 `6082` 这类先按规则匹配（去厂牌前缀、数字核心相等、互相包含） | 规则先行 |
| 标签对齐（兜底） | 规则匹配不上的，让模型输出一张**只有映射关系**的小 JSON，判断不了写 null | 每篇 1 次 |
| 按条件成形 | 一个样品有多个工艺条件时各占一行，成分复制到每一行；同名但成分不同的按不同样品拆开 | 不用 |

关键取舍：**同名但成分不同的记录不会被强行合并**（那多半是两张表里同名不同样品），而是拆成
两行；判断不了的标签一律留空不硬配。成形前后可以在结果面板标题旁看到「成形 979 -> 954 行」，
鼠标悬停能看到继承补了多少格、规则/模型各连上几条、有多少没匹配。

### 多轮定向补全：把首轮漏掉的字段再找一遍

首轮抽完不等于抽完。表格块里没有的工艺参数，往往在实验段落里写着；首轮模型没注意到的
成分列，换个片段就能找到。所以抽完后会自动再跑最多 3 轮"补缺"：

| 每轮做什么 | 说明 |
|---|---|
| 只挑缺字段的记录 | 已经填满的记录直接跳过 |
| 只问缺的那几个字段 | 提示词里只给这些 key，不给全部 14 个字段 |
| 只送相关片段 | 按字段分别检索：温度字段找带 `550 °C` 的片段，时间字段找带 `1 h` 的，工艺找正文 |
| 收敛即停 | 某一轮既无新增也无修正就停，不会空跑到上限 |

合并规则（这三条决定多轮会不会把数据搞坏）：

| 情况 | 动作 | 日志里的标记 |
|---|---|---|
| 原值为空 | 填上 | `added` |
| 原值**没有**逐字证据、新值有逐字证据 | 替换 | `corrected` |
| 两边都有逐字证据却不同 | **不覆盖**，保留原值并提示人工确认（通常是不同工艺条件） | `conflict` |
| 新值引文在原文找不到 / 量纲越界 | 丢弃 | `unverified` / `rejected-*` |

每次抽取都会把逐字段变更明细写成 CSV：`data/output/rounds_log_<时间戳>.csv`
（列：轮次 / 记录 / 文献 / 牌号 / 字段 / 动作 / 旧值 / 新值 / 引文），
结果面板标题旁也会显示「多轮补全 +N / 修正 M」，鼠标悬停可看跑了多少轮、
是否收敛、填充率从多少到多少。

> 成本提醒：每条待补记录每轮打 1 次模型。`extract.rounds.max_calls_total`（默认 400）
> 是硬上限；跑大批文献前建议先用 `max_chunks` 控制样本，看一轮的实际收益再放开。

> 为什么不做"整条重抽 3~5 遍"：同一段文本重问一遍，模型给的还是同一批值，后续轮次
> 几乎没有新信息（实测第 2 轮开始只补到 1~2 个字段），成本却按轮数线性涨。
> 真正有效的是换证据来源（按字段检索别的片段），这也是上面这套做法的出发点。

### 右侧显示的是哪一批？以及"抽完了但数据没变"

结果面板标题旁会显示 **「MM-DD HH:MM · N 条」**，就是这批结果产生的时间。看到的时间和
你刚跑的那次对不上，说明你看到的不是新数据。

常见原因是**新一批悄悄失败了**：结果文件没更新，重开页面就把上一批原样显示出来。
现在这种情况会被明确告知：

- 顶部红色横幅：「上一批抽取（时间）失败了，右侧显示的是更早一批的数据」＋具体原因；
- `data/output/web.log` 里有 `[extract] 启动/完成/失败` 的完整痕迹（含异常堆栈）；
- 所有接口异常也会写进日志（`[err] ...`），静默启动时这是唯一线索。

另外两处限制：

- **同一时刻只允许一个抽取任务**。任务在跑时再点「开始抽取」会提示
  「已经有一个抽取任务在跑」（之前会叠出多个并发任务，一起打云端配额、互相覆盖结果文件）。
- **云端返回 429（限流）会自动退避重试**（5 秒、10 秒）：`llm.gen.retries` 控制次数。
  其它错误不反复重试，宁可明确报错也不把整篇拖成几十分钟。真被配额卡住时，
  把 `extract.workers` 调小。

另外注意：**目标 Excel 不要用 Excel 打开着**，否则 `wb.save` 会失败（界面会明确报失败，不会假装写入）。

宽表（列多）可以用结果面板的「展开」按钮切到全屏视图；表头与序号列固定，横向滚动时不会跟丢。

## 十一、控制抽取规模（块数 / 范围 / 并发）

抽取是全流程唯一耗时的环节，成本≈「送进模型的块数 × 每块生成时间」。界面把这三件事都做成了显式控件，开跑前就能看到要花多久。

**1. 抽取范围（模式）** —— 按钮上直接标出该模式**当前会抽多少块**：

| 模式 | 筛选条件 | 5 篇示例文献实测 |
|---|---|---|
| 表格块 | 只要 `kind=table` | **30 块** |
| 自动 | 表格 + 正文里出现「数值+单位」的段落 | **175 块** |
| 全部块 | 不筛选 | **528 块** |

「自动」不用关键词判定。材料论文几乎每页都有"合金/强度/热处理"这类词，只按关键词命中会把 498 个文本块里的 386 个判为"含数据"（约 6 倍无效开销）。改成要求**数字与单位同时出现**后降到 145 个段落，真正带数据的段落不漏。

**2. 最多抽几块** —— 预设 `1 / 3 / 10 / 30 / 不限`，也可直接输入数字。新文献建议先用 `3` 跑一遍看质量，再放开。排序是「表格优先、同类型按页码」，所以截断永远先保证表格。

**3. 并发请求数** —— 1~4，默认 2。**并发不是越快越好**，同一批 3 个块实测：

| 并发 | 墙钟 | 抽出记录 |
|---|---|---|
| 1 | 392 s / 445 s（跑两次） | 9 条 / 10 条 |
| 2 | 310 s | 8 条 |
| 3 | 372 s | 5 条 |

并发上去后 LM Studio 会把请求合批，单块输出被压短，**记录数随之下降**（3 并发比 1 并发少抽约一半），
墙钟也没继续变快。所以**本地模型**：要最全 → 1；要快 → 2；≥3 明显丢数据（界面给红色警告）。

**云端模型没有"合批压短"这个问题**，瓶颈只来自你的配额，所以默认并发已提到 **4**，
上限 `extract.max_workers`（默认 8），界面滑杆范围跟着这个值走，后端再夹一层硬上限。
被限流（返回 429 / 超时）就往下调。`extract.batch_chunks` 也可以试着开到 2~3
（一次请求塞多块，省往返），但字段多的模板容易撞 `max_tokens` 反而丢记录。

**4. 分批抽取与「继续抽取」** —— 一批抽完后，按钮区会出现
「**▶ 继续抽取（已抽 N 块，接着往下）**」：点它从上次完成的位置接着抽，不重头再来。

原理：前端记录**已抽过哪些块**（每批完成时服务端会上报该批的 `chunk_id`），
续抽时把这份 id 列表作为 `skip_ids` 传回，后端在 `pick_chunks` 里直接排除它们。

**为什么不用"跳过前 N 块"**：那个方案依赖块列表顺序不变。一旦切换抽取范围
（换文献、或在「表格 / 自动 / 全部」之间切换），列表就变了，`skip=10` 会指到完全不同的位置——
要么重复抽、要么漏抽，所以早期只能把进度清零，用户体验就是"换个范围，继续抽取就没了"。
按 id 排除与顺序无关，切换范围后依然准确，因此现在**无论怎么切范围，「继续抽取」都保留**。

进度怎么保存（三道保险，任意一道生效就能续抽）：
1. **浏览器内累积**：每批完成的服务端事件带上该批 `chunk_id`；
2. **localStorage**：刷新/关页面后仍在（点「开始抽取」才算全新开始，会清空）；
3. **服务端 `/api/extract/running`**：重新开页面时接管上一个任务，把它已完成的 id 合并回来。

已抽出的**数据**单独落盘（`data/output/last_extract.json`）。这一份不能只靠内存：
关页面 → 服务自停 → 进程没了，而进度在浏览器 localStorage 里，于是重开后按钮还在、
跳过也照常，唯独右边的结果面板空了。落盘后每次启动读回一份，续抽的批次在盘上累加，
所以重开后仍是**全部批次**的结果，不是只剩最后一批（默认 24 小时内有效，见上文）。

> 服务端事件原来是「一条 Queue，取走就没」：刷新页面后新连接会和旧连接**抢同一条队列**，
> 进度事件被分掉，新页面拿不到 `chunk_id` → 按钮条件（已抽 > 0）不成立 → 「继续抽取」消失。
> 现在改成**事件日志 + 每订阅者一个游标**：多标签页互不干扰，后连的先补发历史事件；
> 收尾的 `done` 事件还会带一份**本批完整 chunk_id 清单**，哪怕进度事件全漏也能补上。

点「开始抽取」（不带继续）才是全新开始。命令行：`python run.py fill --max-chunks 10`，
下一批手动指定 `--skip-ids`（由前端自动处理时无需关心）。

**改了前端源码后必须重新构建**（`web/` 下 `npm run build`，产物落到 `rag/web/dist`）：
界面是构建产物，不重新构建就还是旧页面。首页已加 `Cache-Control: no-store`，
重新构建后刷新即可拿到新页面，不用再清浏览器缓存。

### 抽取准确性：字段-数值对齐 + 合理性校验

成分抽取（Si / Mg / Cu…的质量分数）最容易出的事故是**字段名与数值错位**：
文献里一张 ΔGseg（晶界偏聚自由能，kJ/mol）的表，列名带 of Mg / of Si，
模型把 −9.127 填进 Mg 的质量分数——而引文校验是**逐字命中**的，照样通过。
所以在这之上又加了两层：

**1. 对齐校验**（`extract.alignment`）：字段名必须能在表头/行首找到**对应的那一列**，
确认不了就留空并标注「未识别」，绝不猜一个填上。

| 表头写法 | 判定 |
|---|---|
| `Si`、`Si (wt.%)`、`Element Si`、`Mass fraction of Si` | 可对齐 |
| `of Mg`、`ΔGseg Gb of Mg`（热力学列，不是成分列） | 未识别 → 留空 |

默认只对 `composition` 分组生效（最易错位，且元素符号在表头里写得很规整），
配置里 `groups` 可以加上别的分组。提示词里也同步加了"按表头定位列、按行取单元格、
单位以列为单位、禁止跨量纲搬运"的硬性要求。

**2. 合理性校验**（`extract.sanity`）：按元素设质量分数上限，越界即删字段或标异常。

| 规则 | 默认 |
|---|---|
| wt.% 超出 0~100、或低于基体下限 | 删字段 |
| 超出该元素常见上限（Si 25、Mg 12、Cu 10、Zn 12、Fe/Mn 2、Cr 0.6…） | 删字段 |
| 一条记录里成分合计 > `sum_max_wt`(105) | 删整条 |
| 一条记录里越界字段 ≥ `drop_row_if_violations`(3) | 删整条 |

删掉的东西不会静默消失：都会进 `dropped` 并在界面"已过滤"里写明原因。
上限表在 `config.yaml` 的 `element_max_wt`，**按你的合金体系自行覆盖**。

**5. 耗时显示与预估** —— 界面只显示**已用时间**（每秒刷新，与块完成事件解耦，不会卡住）。
**剩余时间预估已移除**：单块耗时 9~210 秒差异过大，任何外推都不可靠，给错的数字不如不给。

开跑前仍有粗估（「本次计划 N 块 · 预计约 M 分钟」），首次用 `config.yaml` 的
`extract.sec_per_chunk`（默认 60 秒）估，跑完一次后改用**本机实测墙钟**
（指数平滑，并按并发数换算），越用越准。它只用来帮你决定块数，不作为进度承诺。

**6. 计时与页面状态解耦** —— 计时器挂在顶层，切到问答/索引或最小化都不影响；
刷新或手滑关页面后（15 秒内重开），页面会自动接管正在跑的任务，
**已用时间接的是任务真实起点，不会从 0 重数**，进度与最终结果也不丢。

命令行同样可控：

```bash
python run.py fill --mode table --max-chunks 3     # 先抽 3 块看质量
python run.py fill --workers 3                     # 并发 3
```

想进一步加速，最有效的三个杠杆依次是：

1. **减少块数**（线性收益，最有效）—— 30 块就是 30 次调用，砍到 3 块就是 1/10 的时间。
2. **精简字段**（实测 94 → 7 字段：210.8s → 102.6s）—— 输出长度与字段数近似成正比，
   但每块仍有约 100 秒的固定开销（prefill + 采样），所以收益约一半封顶。
3. **提高并发**（2 并发比 1 快约 1.3~1.4×，代价是少抽约 1~2 成记录）—— ≥3 会明显少抽，慎用。

**随时可以停**：抽取中界面会出现「■ 停止」按钮，点它之后正在跑的几块收尾即停，
**已抽完的部分照常返回**，不会白等几十分钟。命令行用 `Ctrl+C`（界面走的是同一个
`should_stop` 回调，语义一致）。
